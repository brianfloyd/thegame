# Filesystem Organization Patterns & Rules

**Purpose**: This document captures established patterns for organizing documentation files in this repository. **MUST BE READ** before implementing any file operations, moves, renames, or reorganization tasks.

---

## Core Organization Principle

This documentation library uses a **numbered, flat structure** (Dewey-Decimal style) where:
- Filenames dictate hierarchy (numeric prefixes)
- Each file contains **one domain only**
- No duplication
- Files are **canonical** and **non-overlapping**

---

## Established Numbering Conventions

### 00-Series — Start Here
- **00-README.md**: Master index and catalog of all documentation
- Always start here to understand the library structure

### 10-Series — GAME OPERATIONS
**Purpose**: Core game systems, player-facing logic, and gameplay mechanics

**Contains**:
- Player architecture
- Room/item systems
- Commands and gameplay flows
- Game engines (harvest, crafting, automation)
- Formula specifications
- God mode editor specs (gameplay functionality)

**Key Pattern**: These are **gameplay-focused** specifications, not technical architecture.

**Examples**:
- `10-01-player-architecture.md`
- `10-04-commands.md`
- `10-06-npc-harvest-engine.md`
- `10-15-god-mode-editors.md`

### 20-Series — ARCHITECTURE
**Purpose**: Technical implementation, frontend/backend architecture, and system design

**Contains**:
- Frontend architecture (client-side structure, components)
- Backend services and utilities
- System architecture overviews
- Markup systems (semantics and rendering)
- Communication protocols
- Rendering systems
- Widget system architecture

**Key Pattern**: These are **technical/architectural** specifications, not gameplay rules.

**Examples**:
- `20-01-frontend-architecture-canonical.md`
- `20-02-markup-semantics.md`
- `20-03-markup-rendering.md`
- `20-04-game-communication.md`
- `20-05-terminal-rendering.md`
- `20-06-widget-system.md`
- `20-backend-services-canonical-spec.md`
- `20-system-architecture.md`

### 100-Series — IGNORE/ARCHIVE
**Purpose**: Files that should be ignored by AI systems - archived, deprecated, or legacy documentation

**Contains**:
- Superseded documentation
- Historical reference material
- Deprecated specs
- Files marked for ignore

**Key Pattern**: These files are **not active documentation** and should be excluded from AI context unless specifically referenced.

**Examples**:
- `100-ignore-factory buff mechanics from chuck`
- `100-god-mode-editors-canonical-answers.md` (superseded by `10-15-god-mode-editors.md`)
- `100-god-mode-editors-canonical-scrub-answers.md` (superseded by `10-15-god-mode-editors.md`)

## Critical Classification Patterns

### Frontend vs Game Operations (10 vs 20)

**Rule**: If a document describes **how the client/browser renders, displays, or communicates**, it belongs in **20-series**.

**If it describes game mechanics, rules, or player-facing logic**, it belongs in **10-series**.

**Examples of correct classification**:
- ✅ `10-04-commands.md` - Game command grammar (gameplay)
- ✅ `20-04-game-communication.md` - WebSocket protocols (architecture)
- ✅ `10-13-widget-system.md` - Would be gameplay widgets
- ✅ `20-06-widget-system.md` - Widget architecture (technical implementation)

**Migration Pattern**: When files are misclassified, move them:
- Frontend architecture docs from 10-series → 20-series (sequential numbering starting at 20-01)
- Game operations stay in 10-series

### Deprecation Pattern (→ 100-series)

**Rule**: When a file is superseded or deprecated:
1. Move to 100-series with descriptive name
2. Keep `100-ignore-` prefix or `100-` prefix for archived files
3. Update `00-README.md` to note the superseding document
4. Mark in README as "archived, superseded by X"

**Examples**:
- Old god-mode Q&A docs → `100-god-mode-editors-canonical-answers.md` (superseded by `10-15-god-mode-editors.md`)
- Deprecated mechanics → `100-ignore-factory buff mechanics from chuck`

## File Naming Patterns

### Standard Format
```
{number}-{descriptive-name}.md
```

### Numbering Rules
1. **Sequential numbering within series**: Use increments (20-01, 20-02, 20-03...)
2. **Sub-numbering for related files**: Use letters (10-01a-player-state-model.md)
3. **Consistent naming**: Use kebab-case, descriptive names
4. **Canonical indicator**: Use `-canonical-` in name if it's a canonical specification

### Examples of Good Names
- `20-01-frontend-architecture-canonical.md`
- `10-01a-player-state-model.md`
- `20-backend-services-canonical-spec.md`
- `100-ignore-factory buff mechanics from chuck`

## Reorganization Workflow

When reorganizing files:

1. **Read this file first** (`999.0 - filesystem readme.md`)
2. **Read `00-README.md`** to understand current structure
3. **Check classification rules** above to determine correct series
4. **Move files** using appropriate numbering
5. **Update `00-README.md`** to reflect:
   - Removed entries from old locations
   - New entries in correct series
   - Any deprecation notes
6. **Update series status** in README if applicable

### Example: Moving Frontend Docs from 10 to 20

```
Before: 10-09-markup-semantics.md (in 10-series)
After:  20-02-markup-semantics.md (in 20-series)

Actions:
1. Move file: 10-09-markup-semantics.md → 20-02-markup-semantics.md
2. Remove from 10-series section in README
3. Add to 20-series section in README
4. Update numbering conventions section
5. Update status section
```

- ✅ Technical implementation specs

- ✅ Communication protocols
- ✅ Component/system architecture
- ❌ NOT gameplay rules
- ❌ NOT game mechanics

### 100-Series Contains:
- ✅ Deprecated documentation
- ✅ Superseded files
- ✅ Historical reference
- ✅ Files marked "ignore"
- ❌ NOT active documentation

## Maintenance Rules

1. **Before moving/renaming files**: Read this document and `00-README.md`
2. **After moving files**: Update `00-README.md` immediately
3. **Numbering gaps are intentional**: Missing numbers (e.g., 10-09 through 10-13) indicate files were moved
4. **Always preserve file history**: Use git moves when possible
5. **Update README status sections**: Keep current status accurate

---

## Anti-Patterns (Don't Do This)

❌ **Don't** put frontend rendering docs in 10-series  
❌ **Don't** put gameplay mechanics in 20-series  
❌ **Don't** skip updating README after moves  
❌ **Don't** create duplicate content across series  
❌ **Don't** put active docs in 100-series  
❌ **Don't** use inconsistent naming conventions
